# Decisions

Product and engineering decisions, with the options considered and why. Newest last.

| # | Decision | Options | Choice and reason |
|---|---|---|---|
| D-001 | Language of the core | Rust; TSX with Rust helpers | **Rust for everything but screens.** The core (S3, credentials, jobs, probes, decoders) is testable without a UI and survives a UI change; TSX holds presentation only. |
| D-002 | Native Shell version | crates.io 0.4.0; a git commit | **`longbridge/nsh` at commit `ec8430f` (13.0.0; was `1662115`)** (0.4.0 + main), in `Cargo.toml` (`rev = …`) and in CI's nsh install (`NSH_REV`). The CLI must match the crates it links; a commit pins both. |
| D-003 | SigV4 | `aws-sigv4`; our own | **Our own (`s3raw::sigv4`, ~150 lines)**, tested against the AWS SigV4 test suite and the S3 documentation's examples. It exposes the canonical request and string to sign, which a diagnosis tool wants, and handles `STREAMING-UNSIGNED-PAYLOAD-TRAILER` and deliberate clock skew for probes. |
| D-004 | HTTP | `reqwest` + rustls; hyper | **reqwest with rustls and native roots**: custom CAs per endpoint, no OpenSSL (static-libc binaries). Redirects are not followed: a 301/307 is a finding (wrong region / addressing). |
| D-005 | Where the listing lives | rows in JS; rows in Rust | **Rust (`Listing` class)**; TSX asks for the visible window. 100 000 rows never cross into the VM. |
| D-006 | Rust ↔ TSX types | typed `JsObject` structs; JSON | **JSON (`JsonValue`) mirrored by `app/src/types.ts`.** Deriving NSH traits on core types would make `sonde-core` depend on NSH, which the layering forbids; a second set of structs in `sonde-nsh` would duplicate every type. |
| D-007 | Static keys in the UI | a form field; config file only | **Config file only.** A key typed into TSX would pass through the JS VM; static keys are for local test servers and live in `config.toml` (0600). |
| D-008 | Destructive confirmation | a checkbox; typed text | **Typed text**: the number of items (many) or the bucket name (one item, lifecycle). Plans expire in 10 minutes and run once. |
| D-009 | Hermetic UI tests | mock in TSX; a server | **A demo S3 server in `sonde-core::demo`** (in-process, 127.0.0.1): real HTTP through the real client, with versions, delete markers, uploads, 100 000 synthetic keys and the real decoder samples. It doubles as `sonde tui --demo`. |
| D-010 | The terminal host | `nsh run --target tui` / `nsh-tui-host`; our own loop | **Our own loop on `nsh-platform-tui`** (FINDINGS #2): one binary embeds the bundle, takes sonde's CLI arguments, and the four places of the app. |
| D-011 | Plugin views in the macOS app | a custom AppKit host; degrade | *(Superseded by D-031.)* **Degrade the presentation**: `nsh package --target macos` builds NSH's runner, which hosts one app; the app manages plugins and opens their views in `sonde tui`. The plugin mechanism (verification, trust, revocation, sandbox) is the same. |
| D-012 | Plugin capability policy | trust the package; check | *(Superseded by D-031.)* **Check at install**: only `host` calls under `sonde.read.*`; any other key must grant nothing (`nsh publish` writes every key). Checked again when a plugin opens. |
| D-013 | Second S3 implementation for CI | Ceph RGW; Garage; SeaweedFS | **Ceph RGW (`ceph/daemon demo`)** as the spec asks, plus **RustFS** (MinIO-compatible, starts in seconds) in CI; MinIO is optional (D-023). |
| D-014 | Iceberg sample | hand-written JSON/Avro; pyiceberg | **pyiceberg 0.9.1** (`tools/gen_iceberg.py`): a real table with appends, an overwrite, a delete, an orphan and expirable snapshots. |
| D-015 | Woodpecker sample | a running Woodpecker; its codec | **Woodpecker's own codec** (`tools/gen-woodpecker`, Go, module at commit 3a8ce69) laying objects out as its object-storage writer does; running Woodpecker needs etcd and MinIO, which CI has no reason to host. |
| D-016 | lakeFS commits | parse KV dumps; trees only | **Trees only**: commits live in lakeFS's KV store, not in the bucket; each metarange is shown as a committed tree, and the UI says so. |
| D-017 | Closed formats | heuristics; cadence only | **Cadence only** for turbopuffer and WarpStream, with "format not published, not decoded" in the UI. |
| D-018 | Probe verdict "differs" vs "fail" | — | **fail** when a guarantee breaks (a condition ignored, a wrong checksum accepted, wrong bytes); **differs** for other statuses or shapes (409 for 412, uuid version ids). |
| D-019 | Exit codes | 0/1; graded | **Graded** (docs/cli.md): CI can fail on broken guarantees (1) and still report differences (2). |
| D-020 | Linux binary | musl; glibc on an old base | **glibc, built on Ubuntu 22.04** (glibc 2.35): only libc/libm/libgcc_s; QuickJS's C build is untroubled; runs on Debian 12 slim (checked in CI). |
| D-021 | Config path on macOS | `~/.config/sonde`; Application Support | **`~/Library/Application Support/sonde`**, the platform's convention; `$SONDE_CONFIG_DIR` and `$XDG_CONFIG_HOME` override on both. |
| D-022 | App capabilities | `fs` for exports; none | **`clipboard`, `notifications` (a run ended) and `windows` (a session in its own window)**, and since 3.0 `picker` (open a `.sonde` file, whose text Rust checks and stores): Rust writes every file; the VM needs no `fs` or `network`. |
| D-023 | Integration targets in CI | MinIO + Ceph RGW + RustFS; Ceph RGW + RustFS | **Ceph RGW + RustFS**: MinIO stopped publishing public images (Docker Hub and Quay refuse anonymous pulls), so its job could not start. `scripts/integration.sh minio` still runs it with `MINIO_IMAGE` set to an image you can pull. |
| D-024 | macOS runners | macos-13 / macos-14; macos-15 / macos-15-intel | **macos-15 (arm64) and macos-15-intel (x86_64)**: the older images never got a runner. |
| D-025 | Direction for 1.0 | a findings dashboard over bucket state; the traffic between an application and its store | **The traffic.** sonde's edge is protocol truth (raw exchanges, SigV4, vendor behavior, layout decoding); a cost advisor over bucket state competes with the cloud's own tools. 1.0 records what software does (`sonde run`), explains it (operations, not requests), and replays it on other endpoints. Bucket scans stay, as one more source of requests. |
| D-026 | How the recorder sees requests | an HTTPS MITM proxy with a local CA; an S3 endpoint that re-signs | **A local S3 endpoint that re-signs.** No CA to install, no TLS interception, and the application never holds the real credentials (it gets dummy keys; sonde signs). Signed `aws-chunked` bodies are decoded because their chunk signatures chain from the client's key; presigned URLs are re-signed. |
| D-027 | 404 on GET/HEAD in summaries | errors; their own count | **Their own count ("not found")**: stores probe for keys that do not exist yet (SlateDB looks for the next manifest and WAL this way, 116 of its 172 requests in the sample run). Counting them as errors would make every healthy run look broken. |
| D-028 | Replay | re-send recorded bytes; re-enact requests | **Re-enact.** Sessions keep no object data (size, privacy) and endpoints hand out their own upload ids, ETags and tokens, so replay sends synthetic payloads of the recorded length, keeps control documents, maps identifiers as it goes, and confines every key to a fresh prefix. Comparing status and S3 code catches what matters for correctness — a conditional write that should have failed, a missing feature — without false alarms from ETag or timing differences. |
| D-029 | Direction for 2.0 | more sections; one place to start | **Run is the home.** Typing a command and watching its terminal next to its operations is the shortest path to sonde's point; the session that results holds both, lined up in time. Everything else is reached from it. |
| D-030 | Navigation | nine sections in a sidebar; a few places and a palette | **Four places (Run, Sessions, Store, Settings) and a command palette.** The bucket tools live under Store as tabs, configuration and logs under Settings; every place, tab and action is in the palette (⌘K, `:` in the terminal). |
| D-031 | Plugins | keep; remove | **Remove.** Signed packages, trust roots and revocation cost a screen, a CLI group and a sandbox to explain, and their views could open only in the terminal (the macOS runner hosts one app). Layout decoders stay built in; supersedes D-011 and D-012. |
| D-032 | The program's output | a log file next to the session; in the session | **In the session** (`{"log": …}` lines with arrival times), so one file carries what was printed and what was requested, and alignment needs no second clock. |
| D-033 | Sharing a session | a hosted service; a static site | **A static site** (`sonde share`): the viewer built with Native Shell's web target from the app's pure views, and a document computed in Rust. No Rust in the browser, nothing to run, any host. |
| D-034 | Desktop platforms and updates | macOS only; macOS, Linux, Windows | **macOS, Linux (GTK 4) and Windows**, one TSX app, built by CI. Updates through Native Shell's updater from GitHub Releases (`latest.json`, SHA-256 checked), only when the user asks. |
| D-035 | The look of 2.1 | restyle screens one by one; a design system first | **A design system first**, as Native Shell's design guide asks: semantic tokens for what sonde shows (request outcomes, storage formats, the toolbar, the inspector), one icon family (Lucide on a Canvas, in token colors), the app's own styled layer on nsh/base (Tabs, Tooltip, Toast, Sheet, AlertDialog, Collapsible, Combobox, Tree, Command, DataTable's parts), then the pages from it. |
| D-036 | Where details go | a third fixed column; pages; an inspector | **An inspector**: a resizable panel beside what it details (an operation, a request, an object), closed from its bar; in a narrow window it comes in from the edge as a Sheet and the sidebar folds away, so the table keeps its room. |
| D-037 | The window's chrome | the system's title bar; the app's own | **The app's own** (`titleBar: hidden`): one toolbar for where you are, the program running, the endpoint, the lock and search, instead of a title bar and a header repeating each other. On Linux and Windows, whose menu bar goes with the system's title bar, the toolbar has a menu button (`Menu.popup`). |
| D-038 | Saving settings | a Save button; as they change | **As they change**, a toast with Undo: a setting is a decision already made when it is changed. |
| D-039 | A visual check | screenshots by hand; in CI | **In CI**: `scripts/shots.sh` drives the app on a real GTK window under Xvfb through every place, wide and at the least size, light and dark, English and Chinese; the PNGs are each build's artifact. Behavior tests cannot see a clipped column or an unreadable header. |
| D-040 | Direction for 3.0 | more features; fewer places that do more | **Fewer places.** Three in the sidebar (Run, Sessions, Buckets); what is configured once (Settings) or looked at now and then (sonde's own activity, compatibility) leaves the main window. No new features: the same tools, reached without forms. |
| D-041 | Bucket tools | tabs with a prefix form and a Scan button; an overview | **An overview** above the objects: the cheap facts (incomplete uploads, versioning, recognised layouts) are fetched as a bucket or prefix opens, the costly one (size: every object and version listed) only when asked; a card shows only when it has something to say, and opens its detail in a sheet for the prefix on screen. A terminal keeps the tabs. |
| D-042 | sonde's own requests, jobs and audit log | three pages; one sheet | **Activity**, a sheet from the toolbar: they answer one question — what is sonde doing, what did it do — and are rarely the reason to open the app. |
| D-043 | Localising the analysis | translate English strings in the UI; structured phrases | **Phrases**: the Rust analysis emits a key and its arguments beside its English text; the app and the web viewer render them from templates in each language, falling back to the English text. The CLI's English is produced from the same templates, so the two cannot drift (a test reads every recorded session and checks). |
| D-044 | Compatibility | a tab under Buckets; from the endpoints | **From the endpoints**, in a window of its own: it is about endpoints, runs on several at once, and takes minutes. |
| D-045 | Materials | opaque surfaces; glass | **Glass on what floats, on macOS** (`glassEffect: "regular"` with a `backdropFilter` blur to fall back to, on a translucent fill): the palette, sheets, hover cards and menus sit over content; the toolbar and sidebar, over nothing, stay opaque. On Linux and Windows the fill stays opaque: the screenshots showed text through an unblurred translucent card. |
| D-046 | Direction for 4.0 | new features; the design guides applied throughout | **The guides, throughout.** No new feature: every page measured against Native Shell's design guides (task first, hierarchy, tokens, one surface per kind, primary as the default commit, platform before web habit), the standards written down in `app/DESIGN.md`. |
| D-047 | Type | sizes per page; a scale | **Five roles** in `tailwind.fontSize` (caption 11, small 12, body 13, heading 15, title 20): a desktop scale around a 13 pt body, as macOS's own; live figures in tabular digits; the platform's monospace only for identifiers, code and time columns (a shipped face was dropped: FINDINGS 15). |
| D-048 | A session's findings | chips with a card on hover; a list | **A list**, folded or open: the finding, why it matters and the operations it narrows to, in place. The guide's rule: a core result is not reduced to a chip, and a hover never carries what a reader needs. |
| D-049 | Overlays | each page its own sheet and popup; one of each | **`SidePanel` and `POPUP`**: three panel widths, one header, one scrim token; one popup surface for every anchored menu. |
| D-050 | The platform | the app's own surfaces everywhere; the system's where it has one | **The system's**: the window's sidebar material (`backdrop`), Dock and taskbar progress (`progress`), the represented file and window tabs for session windows; an error boundary per place instead of a blank window. |
| D-051 | Direction for 5.0 | more surfaces; the core result made right | **The core result made right.** A review of 4.0 for bugs first (ten fixed, each with a regression test), then what a session finds made faster (analysis off the interface's thread, cached per version of the file) and more useful (three findings, ranked, with what acting on them saves), and sessions made things to look after (rename, delete, search, share, drop, Open Recent). No new place. |
| D-052 | Ranking findings | by kind; by the requests they bear on | **Warnings first, then by the requests a finding bears on**, with a saving where it can be counted (a cache reads a hot key once; one PUT replaces a small multipart upload). A count of requests is what a session can measure honestly; money and time depend on a store and a network it did not see. |
| D-053 | Throttling advice | a fixed concurrency; what the session shows | **What the session shows**: the fewest requests in flight when the store throttled one. Under that many at once it did not; with four or fewer in flight the finding speaks of the rate per prefix instead. |
| D-054 | Sharing from the app | copy the CLI command; write and serve the page | **Write and serve the page** (`sonde share`'s site, under the data directory, on 127.0.0.1) and open it in the browser; the folder is what you put on a web server to send it. The viewer is embedded once, in `sonde-proxy`, for the CLI and the app; a build without it falls back to copying the command. |
| D-055 | A session's titles | rewrite the session file's header; a file beside the sessions | **`titles.json` beside the sessions**, by file name: a session file stays as it was recorded (and shared), and renaming a 50,000-request session costs nothing. |
| D-056 | Direction for 6.0 | more findings; time and cost, seen | **Time and cost, seen.** A review of 5.0 for bugs first (nine fixed, each with a test), then what a session cost in time and money computed in Rust (`profile.rs`), two runs compared, and every chart moved to Native Shell's Plot: one question per chart, said in words too. No new place. |
| D-057 | A kind's time | latencies added; wall-clock union | **The union of its requests' intervals**: ten reads at once for 50 ms are 50 ms of the program's waiting, not 500. Shares are of the time any request was in flight, so they add up to about 100% and say what the program waited on. |
| D-058 | Request cost | none; S3 Standard's prices, configurable | **S3 Standard's (us-east-1) by default**, writes and listings at one price, reads at another, deletes free (`settings.prices.per-1000-writes`, `per-1000-reads`). An estimate for comparing runs, not a bill. |
| D-059 | Charts | the app's own canvases; Native Shell's Plot | **Plot**: the marks drawn natively from the rows, hover, tooltips, fading and the keyboard handled in Rust, motion on the platform's animator, accessibility built in. The hand-drawn timeline redrew its canvas on every mouse move; its drag-to-zoom gives way to a slice picked on the session's shape. |
| D-060 | Comparing two sessions | answers only; before and after too | **Before and after first**, unless one is a replay: two runs of a program are compared by what a change did (requests, waiting, cost, by kind; findings gone and new); a replay still opens on its answers, request by request. |
| D-061 | Direction for 7.0 | one session deeper; a program over its runs | **A program over its runs.** A session explains a run; most questions are about a change: did it help, did it break the budget. Runs of one command are grouped, a run may be the baseline, and every run is held to it — in the app (Runs) and in CI (`sonde check`). |
| D-062 | What a program is | a name the user gives; the command | **The command, spaces collapsed**: nothing to set up, and two runs of `python etl.py --day 1` are the same program. Replays and recordings without a command have none. Baselines live in `baselines.json` beside the sessions, by file name. |
| D-063 | Gating CI | a new tool; `sonde check` | **`sonde check`**: absolute budgets (requests, waiting, cost, errors) and a baseline with a tolerance (10% by default) and no new warning; a table, or JSON, and exit 1 when over. The same check the app shows. |
| D-064 | Prefix rates | S3's documented limits; measured limits | **S3's documented 5,500 reads and 3,500 writes a second per prefix**, a prefix being a key's folder (three levels): a finding at half, a warning past 80% or when throttled. Other stores differ; the finding says the figure it compares with. |
| D-065 | The flow chart | per request; per kind and prefix | **Operation → prefix → outcome**, the top six operations and eight prefixes, the rest as "other": a Sankey reads at a glance only with few nodes; the table and the heat map hold the detail. |
| D-066 | A monospace font of its own | bundle one (JetBrains Mono, OFL); the platform's | **The platform's, named `ui-monospace`**: SF Mono, Consolas, fontconfig's monospace. A bundled font is measured narrower than drawn on GTK (FINDINGS 15), which cuts the last glyph of a cell; Native Shell keeps a font token's first family only (FINDINGS 18), so the generic name first is what reaches every platform. |
| D-067 | Production traffic | a log shipper; read the logs sonde is given | **Import**: an S3 server access log, CloudTrail data events or a HAR becomes a session (`sonde import`, or open it in the app), so the same findings read production with no proxy. What a source lacks stays empty (CloudTrail has no latency). |
| D-068 | The timeline | a pane of its own; the operations' When column | **The When column**: a Gantt beside a table that already places each operation in time showed the same thing twice; the shape above both, with the findings' numbers on it, says when. |
| D-069 | Updating sonde's code | new apps only; signed packages too | **Signed packages too**, once the project has a root and a release key: the release signs the TSX as a package (`nsh publish`), the manifest offers it, and an app that trusts the root runs it after a restart. Without the keys the step is skipped. |
| D-070 | The run history | Combobox; the system's menu | **The system's menu** beside the command field: a Combobox chooses from a list, and Return would choose a row instead of running the command typed. The terminal shows the last five under the field. |
| D-071 | Views following the engine | timers; the engine's events | **The engine's events** (`Sonde.on("request" \| "jobs")`, a broadcast and a watch channel posted on the engine thread): nothing runs while nothing changes, and a view hears of a change at once. Run's live view still reads its session file twice a second: its records are not in the request log. |
| D-072 | Split views | fixed widths; ResizablePanelGroup | **ResizablePanelGroup**, the widths kept with the app's sizes: a list or a sidebar keeps its width as the window changes (`fixed`); an inspector shares the room, so it never leaves a narrow window. |
| D-073 | Which code sent a request | profilers and stack sampling; a header the program adds | **A header, `x-sonde-caller`**, read and never forwarded; the SDK from the user agent, the trace from `traceparent`. For Python an opt-in `sitecustomize` sets it before signing (botocore's own event); other languages set it with their SDK's hook. Nothing is injected unless asked. |
| D-074 | A project's budget | flags in CI files; a file in the repository | **`sonde.toml`'s `[check]`**, found from the working directory to the repository's root; flags win. The same budget gates CI, alerts from `watch` and reads in review (`-f markdown`). |
| D-075 | Sharing of the time | each kind's busy time; split among requests in flight | **Split among the requests in flight**: a moment two kinds overlap counts half for each, so the kinds add up to the waiting (no share above 100%). |
| D-076 | Activity's requests | one inspector in Activity; sonde's requests as a session | **Both**: the inspector stays (an error's request is a press away) and "Open as a session" reads sonde's own requests with findings, time and compare like any run's. |
| D-077 | The run history field | Combobox; the system's menu | Kept from D-070: Return runs what was typed. |
| D-078 | The look of the app | Native Shell's own look; a kit of the app's | **The app's kit** (`ui/kit.tsx`): Native Shell's base components have behavior and no look by design, so the look is the app's — but only there. Each kit piece wraps one nsh export with theme tokens (one card, one table, two heading levels, four buttons, one focus ring); a page never styles a base control itself, and `scripts/lint-kit.py` fails CI when one does. |
| D-079 | Disclosure | a Button and a Collapsible; Accordion | **Accordion** (one item where one is needed): a real heading and a trigger that says it is expanded, which a Button with `selected` could not. |
| D-080 | Requests drawn one by one | the slowest 400; all, up to 4000 | **All of a session up to 4000, else the slowest 400 and an even spread of the rest**: the slowest alone drew only the tail, which reads as a slow program. Plot has no log scale: values are drawn as their logs and the ticks say the times. |
| D-081 | A run and its commit | none; git, then CI | **`git` in the folder it ran in, else `GITHUB_SHA`**, with the branch and whether it had uncommitted changes. It ties "past the baseline since…" to the change between two commits; shared pages keep the commit and drop the folder. |
| D-082 | Production from logs | a daemon; `sonde watch --logs` | **`watch --logs`** in the CLI (the app opens what it writes): it reads with the endpoint's credentials, GET and LIST only, each pass a run of `logs of s3://…` so it has a baseline and `sonde check` like any program. |
| D-083 | Prices per view | the settings'; the session's endpoint's | **The session's endpoint's** (the settings' while changed, else its vendor's): one price per session in every view and in the CLI. |
| D-084 | Callers beyond Python | none; a hook per SDK | **A hook per SDK, loaded by the language's own variable** (`NODE_OPTIONS`, `JAVA_TOOL_OPTIONS`), each adding `x-sonde-caller` only to requests to sonde and never stopping the program. Java's interceptor is added only when the SDK is on the system class path: a class loader of its own (Spring Boot) could not load it, and failing would break the program. |
| D-085 | Latency | to the headers; the whole exchange | **The whole exchange, and the first byte beside it**: a program waits for the body too. The proxy logs a record when its body has gone through (or the program stopped reading). |
| D-086 | Logs without times | zeros; nothing said | **Nothing said of how long**: CloudTrail has no request times, so a session of one has no latency charts, waiting or latency findings, rather than zeros that read as fast. |
| D-087 | Findings kept on purpose | none; `expect` in `sonde.toml` | **`expect`**: a finding's identity, kind or words; never a new warning, listed as expected. The project says it, with its code; the app only copies the line. |
| D-088 | Sizes | each control its own; tokens | **Tokens (`CONTROL`, `ROW`, `FORM`) and a lint**: two control heights and three row heights; 12.0 found five of each. |
| D-089 | The window's columns | sidebar, a list, the place, an inspector; two columns and an inspector | **Two columns.** 12.0's sidebar held three rows and nothing else, each place drew a list column of its own in its own way, and the sessions list left whenever an operation was chosen so the inspector had room. The sidebar now holds the places and the current place's list (`showInSidebar`); choosing an operation moves nothing but the inspector. |
| D-090 | A session's page | header, findings, tabs, a pane in what is left; header, tabs, the pane | **The pane takes the room under its tabs.** The findings belong with the operations they narrow; over the Time pane they left the charts a third of the window. The session's shape is a strip over the operations, full width, where its slices filter them. |
| D-091 | The Time pane | charts one under another; a board | **A board**: each chart in one frame (`Chart`), two abreast where there is room, under one timeline whose chosen stretch every chart over time follows. Nine sections in one column was a scroll, not a view. |
| D-092 | Requests in flight | the step line over the shape; lanes | **Both**: the line says how many, the lanes which ones. Plot has a bar per row, not several on a band, so the lanes are cells on a grid of time slices (96) by lane (24 at most); a request shorter than a slice is one cell. |
| D-093 | A config that does not load | start empty; start empty and refuse to save | **Refuse to save, and say so**: the app starts without endpoints, a notice names the file and the reason with Reload, and nothing is written until the file loads. A save re-reads the file first and applies only its change, so an edit made meanwhile stays. |
| D-094 | Read-only and probes | probes exempt; refused | **Refused**: a compatibility run writes, deletes and creates buckets. The window says why and where to turn it off; each run is in the audit log. |
| D-095 | A proxied exchange's time limit | 60 s in all; 60 s without a byte | **Without a byte**: an upload or download of any length goes through while it moves. |
| D-096 | Durations | `ms()` and `offset()`; one | **One (`duration`)**, its unit chosen after rounding and up to hours: "184532 ms" and "7200.0 s" were both the old pair's. |
| D-097 | What a fault rule counts | requests as they arrive ("the third UploadPart"); attempts at one request | **Attempts at one request** (its method, place and part): "the third" is a race in a program that sends several at once, and a seed does not make it the same request twice. `times = 1` fails each request's first attempt and lets its retry through, which is also the question asked: does it retry. |
| D-098 | What "survived" means | the data is right; what the requests show | **What the requests show**: every failed request sent again, no more left behind than a clean run leaves, the clean run's exit. sonde does not read a program's data back, and says so. A write dropped in silence (failed, never sent again, exit 0) is "broke". |
| D-099 | A trial's sessions | among the program's runs; a folder of their own | **`trials/` beside the run**: a run under faults has more requests, errors and waiting by design, and as a run of the program it would move the trend, the baseline and "newest". The verdicts are a file beside the run, read by `check` and the app. |
| D-100 | Running a command several times | sonde gives each run a prefix; the command says where | **The command says**: `{trial}` in an argument and `SONDE_TRIAL`. sonde cannot know which of a program's arguments is its place, and rewriting keys in the proxy would make the trial a different program. |
| D-101 | Prefixes in the analysis | three folder levels; whole folders, folded when too many | **Whole folders**, the quietest of the deepest folded into the one above while there are more than a chart holds, the row saying how many it stands for: three levels made `wal/2026/11/` and `wal/2026/12/` one row. |
| D-102 | More engines | a version's theme; whenever there is a recording | **Whenever there is a real recording**: Lance took one fixture and one change. An engine is recognised from a recorded run of it (kept as a test), never from its documentation alone. |
| D-103 | What counts as a retry | a later request with the same method and key; against the clean run | **Against the clean run**: a request the clean run sent *n* times and the trial answered successfully fewer than *n* times was not retried. A program that writes `state` twice by design was read as retrying; the clean run is the only thing that knows what the program does unprovoked. |
| D-104 | A request without a key | one identity per method and bucket; its body and paging | **Its sorted paging parameters and its body's hash** (kept on the record as `x-sonde-body-sha256`): two `DeleteObjects` batches, or two pages of a listing, are two requests. |
